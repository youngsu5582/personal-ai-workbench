# ADR 0004. 서비스별로 생성 자산과 사용을 격리한다

- 상태: 제안 (2026-10-31)
- 범위: 서비스 소유권 · 인증 · 생성 자산 · 사용량
- 관련 결정: [ADR 0001](0001-upload-content-sha256.md) — 소유자 안에서 파일 재사용

## 결정

- 사용자는 하나 이상의 서비스를 가진다. 서비스는 템플릿 · 워크플로 · 생성 작업 · 파일 · 사용량을 나누는 기본 경계다.
- 사용자마다 기본 서비스가 정확히 하나 있다. 새 사용자에게 만들고, 기존 사용자에게는 이관할 때 만든다. 기본 서비스는 삭제할 수 없다.
- 사용자 로그인으로 서비스 범위의 기능을 사용할 때 서비스 선택이 없으면 기본 서비스를 사용한다. 서비스를 명시하면 그 사용자의 서비스인지 확인한다.
- 서비스별 API 키를 발급한다. 키로 호출할 때는 키에 연결된 서비스가 범위다. 요청에 다른 서비스가 지정되면 거부한다.
- 사용자는 자기 서비스들을 관리할 수 있다. 계정 정보와 서비스 목록처럼 계정 범위인 요청에는 서비스를 고르지 않는다.
- 템플릿은 서비스에 속한다. 현재 생성용 템플릿의 코드는 `generation` 에 둔다. 향후 워크플로도 서비스 범위로 관리한다.
- 서비스 관리 책임은 `user` 와 별도의 `workspace` 모듈에 둔다. API 키 발급 · 관리 · 검증은 `auth` 에 둔다.

여기서 서비스는 사용자의 애플리케이션이나 용도별 작업 공간이다. 코드의 서비스 클래스나 별도 배포 프로세스를 뜻하지 않는다.

## 문제와 사용자 영향

현재 생성 작업 · 업로드 파일 · Provider 사용량은 사용자 UUID 로 구분한다. 한 사용자가 여러 애플리케이션을 운영하면
호출과 비용을 서비스별로 나누기 어렵고, 한 애플리케이션의 자격 증명으로 같은 사용자의 다른 데이터까지 접근할 수 있다.
생성용 템플릿도 사용자 범위로 설계되어 있다.

서비스를 격리하면 한 서비스의 키는 다른 서비스의 템플릿과 작업을 사용할 수 없다. 사용자는 로그인해 자기 서비스들을 관리한다.
서비스를 하나만 쓰는 사용자는 기본 서비스를 통해 별도 선택 없이 기존과 비슷하게 사용할 수 있다.

## 선택한 해법

```text
사용자
├── 기본 서비스 ── API 키 · 템플릿 · 작업 · 파일 · 사용량
└── 다른 서비스 ─ API 키 · 템플릿 · 작업 · 파일 · 사용량
```

- 서버가 인증된 사용자와 서비스의 관계를 확인해 요청 범위를 정한다. 클라이언트가 보낸 사용자나 서비스 식별자만으로 소유권을 인정하지 않는다.
- JWT 는 사용자를 식별한다. 사용자가 선택한 서비스의 소유권을 확인하고, 선택이 없으면 기본 서비스를 사용한다.
- API 키는 연결된 서비스와 그 소유자를 확인한다. 키 관리 API 는 사용자 로그인으로만 사용한다.
- 같은 사용자에게 속하더라도 서비스 A 의 키나 서비스 범위 요청으로 서비스 B 의 자산을 조회 · 수정 · 실행하지 못한다.
- 비동기 작업은 접수 시 확정한 서비스 식별자를 저장해 워커의 파일 접근과 사용량 기록까지 전달한다.
- 기존 사용자 소유 데이터는 해당 사용자의 기본 서비스에 연결한다. 기존 기록만으로 과거 호출의 실제 서비스는 구분할 수 없다.
- 파일의 내용 해시가 같아도 접근 권한과 재사용 판단은 서비스 범위에서 한다. 저장 바이트의 물리적 중복 제거 여부와 접근 권한은 별개다.
- 사용자는 자신의 전체 서비스 사용량을 합산해 볼 수 있다. 이는 특정 서비스 하나를 선택하는 요청과 별도로 사용자 소유권을 검증한다.

## 선택하지 않은 대안

| 대안 | 선택하지 않은 이유 |
|---|---|
| 사용자 단위로 자산을 공유하고 키만 서비스별로 나눈다 | 사용량은 구분할 수 있지만 한 서비스의 키가 다른 서비스의 템플릿과 결과에 접근할 수 있다 |
| 템플릿만 사용자 단위로 공유한다 | 같은 사용자의 서비스에 서로 다른 프롬프트와 변경 주기가 생길 때 경계가 모호해진다 |
| 서비스를 `user` 모듈 안에 둔다 | 계정과 로그인 정체성, 서비스의 생명주기와 접근 범위는 변경 이유가 다르다 |
| 모든 요청에 서비스 ID 를 필수로 받는다 | 계정 관리에는 필요하지 않고, 서비스를 하나만 쓰는 사용자에게도 선택을 강요한다 |

템플릿을 다른 서비스에서 재사용할 필요가 생기면 서비스 간 복사를 우선 검토한다. 공유 원본과 전파 규칙은 지금 도입하지 않는다.

## 이행과 검증

- 기본 서비스를 만들고 기존 작업 · 업로드 · 사용량 등 각 소유 데이터를 연결한 뒤 서비스 범위 조회를 적용한다. 적용된 마이그레이션은 수정하지 않는다.
- 실행 중인 작업과 그 작업이 나중에 남길 파일 · 사용량도 같은 기본 서비스에 귀속되어야 한다.
- 같은 사용자의 서로 다른 서비스와 다른 사용자의 서비스에 대해 작업 · 파일 · 템플릿의 접근 차단을 검증한다.
- 키 발급 · 폐기 · 비활성 사용자 및 서비스의 접근 차단과, 키에 연결된 서비스와 요청 범위의 불일치를 검증한다.
- 기존 데이터가 기본 서비스에서 조회되고 서비스별 사용량 및 사용자 전체 합계가 올바른지 검증한다.

## 범위 밖과 다시 검토할 조건

- 크레딧은 구현하지 않는다. 향후에는 사용자 단위 잔액과 서비스별 사용 기록 · 선택적 한도를 출발점으로 별도 과금 설계에서 결정한다.
- 기본 서비스의 이름과 다른 서비스를 기본으로 변경할 수 있는지는 정하지 않는다.
- API 경로 · 키 형식 · 세부 권한 · 서비스 비활성화의 구체적인 동작은 구현 설계에서 정한다.
- 여러 사용자가 한 서비스를 함께 관리하거나, 서비스별 결제 주체 · 독립 잔액이 필요해지면 소유권과 과금 경계를 다시 검토한다.
- 여러 서비스가 템플릿 하나를 함께 수정해야 하는 요구가 생기면 복사 대신 명시적 공유 모델을 검토한다.
