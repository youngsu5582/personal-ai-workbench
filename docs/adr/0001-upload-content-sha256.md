# ADR 0001. 업로드 내용을 SHA-256 으로 고정하고 소유자 안에서 재사용한다

- 상태: 채택 (2026-10-18, #54 머지). 공개 식별자 절은 #55 에서 더했다
- 범위: `upload` 모듈, `storage` 의 키 규칙과 서명, 업로드 클라이언트(`scripts/upload.sh` · 샘플 페이지), 공개 파일 식별자(#55)
- 실험 기록: `.claude/plans/2026-09-27-presigned-upload/INDEX.md` 의 F1–F7 · D7

## 결정

- 발급 요청에 바이트의 SHA-256 을 필수로 받고, 서명에 `x-amz-checksum-sha256` 으로 싣는다. 보관소가 그 해시와 다른 바이트를 거절한다.
- 업로드의 정체성은 `(owner_user_uuid, sha256)` 이다(유니크). 같은 사용자가 같은 내용을 다시 올리면 기존 행을 쓴다.
- 저장 키는 해시로 정한다 — `users/{owner}/uploads/{hash[0..2]}/{hash[2..4]}/{hash}.{ext}`.
  생성 결과물(`blobs/`)과 키 규칙은 같지만 자리는 나눈다.
- 상태는 `PENDING → READY | REJECTED` 한 방향이다. READY 는 다시 검증하지 않고, REJECTED 는 다시 열지 않는다.
- 업로드와 생성 결과의 공개 파일 식별자도 SHA-256 이다(#55). 사용자 · Job · Task 의 UUID 는 그대로 둔다.

## 문제와 사용자 영향

- **발급한 주소로 내용을 바꿔치기할 수 있었다.** presigned URL 은 사용 횟수를 제한하지 않아, 같은 주소로 다시 PUT 하면 덮어써진다(F3).
  Garage 는 조건부 쓰기(`If-None-Match: *`)를 지원하지 않아 1회용 주소로 막을 수도 없다(F4).
  READY 는 다시 검증하지 않으므로, 검증을 통과한 뒤 다른 바이트로 바꾸면 그대로 i2i 입력이 된다.
- **같은 파일을 올릴 때마다 UUID 와 객체가 늘었다.** 키가 `users/{owner}/uploads/{uuid}` 라 같은 바이트도 매번 새 자리였고,
  클라이언트는 이미 올린 파일도 매번 전송했다.

## 제약 조건

- 앱은 업로드 바이트를 보지 않는다. 클라이언트가 보관소에 직접 PUT 한다. 앱이 파일을 받지 않는 것이 presigned 를 고른 이유 전부다.
- Garage 는 업로드 완료 알림을 지원하지 않는다. 앱은 업로드가 끝난 시점을 모른다.
- 서명에 넣은 값만 보관소가 강제한다 — `contentType`(F1) · `contentLength`(F2) · `x-amz-checksum-sha256`(F7).
- 기존 행은 객체를 읽지 않고 해시를 채울 수 없다.
- 사용자 사이에서 같은 해시를 조회하면 남의 파일 보관 여부가 새어 나간다.

## 선택한 해법

### 흐름

```text
클라이언트                          앱                                   보관소 (Garage)
 앞부분 → 형식, 전체 → SHA-256
 POST /api/uploads ───────────▶  (owner, sha256) 조회
   {contentType, contentLength,     ├ 없음     → 행 생성(PENDING) · PUT 주소
    sha256}                         ├ PENDING  → 올라왔으면 검증, 아니면 같은 주소 재발급
                                    ├ READY    → 기존 uuid · uploadRequired=false (PUT 생략)
                                    └ REJECTED → 400 과 사유
 PUT (서명된 헤더 그대로) ─────────────────────────────────────────▶  해시가 다르면 400, 원본 보존
 POST /api/jobs (uuid) ────────▶  처음 쓰일 때 앞부분 Range GET → READY | REJECTED
```

발급 응답의 `headers` 에 `Content-Type` · `Content-Length` · `x-amz-checksum-sha256`(digest 32바이트의 Base64) ·
`x-amz-sdk-checksum-algorithm: SHA256` 이 담기고, 클라이언트는 그대로 보낸다. 요청의 `sha256` 은 소문자 hex 64자다.

### 경로

```text
users/{ownerUuid}/uploads/ab/cd/abcd…(64자).png
└─ 소유자 ─┘└ 자리 ┘└팬아웃┘└─ 해시 ─┘ └확장자┘
```

| 부분 | 이유 |
|---|---|
| `users/{owner}` 가 맨 앞 | 계정 정리가 접두사 하나로 끝난다. 키로 남의 바이트 보관 여부를 떠볼 수 없다 |
| `uploads/` (결과물은 `blobs/`) | 업로드 쓰기 권한으로 결과물을 덮어쓰지 못한다. 거절된 업로드를 지우며 결과물까지 지우지 않는다. 한 객체를 두 행이 공유하지 않아 삭제에 참조 세기가 필요 없다 |
| `ab/cd` 팬아웃 | 해시 앞 네 글자로 나눠 로컬 디스크의 한 디렉토리에 파일이 몰리지 않게 한다 |
| 해시 | 같은 내용이면 같은 키다. 보관이 멱등하고 고아가 생기지 않는다 |
| 확장자 | 사람이 보관소를 열어볼 때 형식을 알아보게 한다. 선언한 형식에서 나오므로 정체성에는 쓰지 않는다 |

키에 `v2/` 같은 판 표시는 붙이지 않는다. 키는 행마다 통째로 저장돼 옛 모양(`users/{owner}/uploads/{uuid}`)과 새 모양이 함께 산다.

### 특징 — 얻는 것과 치르는 것

| 얻는 것 | 치르는 것 |
|---|---|
| 주소가 새도 **같은 바이트만** 올라간다. 바꿔치기가 구조적으로 불가능하다(F7) | 클라이언트가 PUT 전에 파일 **전체를 읽어** 해시해야 한다. 상한이 20MiB 라 지금은 감당된다 |
| READY 를 다시 검증할 필요가 없다. 검증 후 이동(최종 위치로 복사)도 필요 없다 | 크기와 해시를 미리 알아야 해 **스트리밍 업로드가 안 된다** |
| 같은 파일의 재업로드는 PUT 없이 끝난다 (`uploadRequired=false`) | 체크섬 헤더 두 개를 버킷 CORS 에 허용해야 한다. 기존 버킷은 `scripts/upload-cors.sh` 를 다시 돌려야 한다 |
| 재발급이 멱등하다. 같은 내용은 같은 행 · 같은 키다 | 해시가 없는 옛 행은 중복 판정에서 빠진다. 옛 URL 의 조건도 소급해 바꾸지 못한다 |
| 보관소가 전송 중 손상도 함께 잡는다 | 내용 고정이 **보관소의 체크섬 강제에 기댄다.** 보관소를 바꾸면 다시 확인해야 한다 |
| | 잘못 선언해 거절된 내용은 그 사용자가 다시 올릴 수 없다 (아래) |

### 해시가 보장하지 않는 것

해시는 "클라이언트가 말한 그 바이트" 를 고정할 뿐, 그것이 PNG 라는 뜻은 아니다.
그래서 앱은 처음 쓰일 때 앞부분만 읽어 **있는가 · 선언한 크기인가 · 매직넘버가 선언한 형식인가**를 확인한다(`DefaultUploadedFiles.verify`).
디코드와 재인코딩은 이미지를 실제로 여는 Provider 가 맡는다.

### 거절된 파일은 다시 열지 않는다

정체성이 해시라 REJECTED 행이 남으면 같은 내용은 다시 올릴 수 없다. 이름이 `.png` 인 JPEG 처럼 선언만 틀린 경우가 그렇다.

- 형식은 클라이언트가 확장자가 아니라 **매직넘버로** 정해 선언하는 것이 계약이다. 공식 클라이언트 둘이 서버와 같은 규칙으로 선언한다.
- REJECTED 에 다시 오면 형식을 바꿔도 400 과 사유를 돌려준다. 서버가 선언을 정정해 주지 않는다.
- 정정(REJECTED → PENDING)을 구현했다가 걷어냈다. 행을 재사용하자 정정 전 검증이 새 PENDING 을 덮는 경우(`updated_at` 대조),
  동시 정정(재시도 루프 · 409)을 다뤄야 했는데, 공식 클라이언트에서는 생기지 않는 경로였다.

### 동시성

| 경우 | 처리 |
|---|---|
| 같은 파일의 동시 최초 발급 | 유니크 제약이 한 행만 남긴다. 걸린 쪽은 트랜잭션 밖에서 상대가 만든 행을 다시 읽는다 (user 모듈 `resolveOrRegister` 와 같은 방식) |
| 같은 파일의 동시 검증 | PENDING 일 때만 옮기는 조건부 UPDATE. 이긴 쪽만 기록하고 객체를 지운다 |

### 공개 식별자 (#55)

#54 는 기존 계약대로 UUID 를 밖에 냈다. 그런데 소유자 안에서 UUID 와 해시는 1:1 이라 UUID 는 간접 참조일 뿐이고,
지킬 근거였던 알고리즘 고착도 키와 서명이 이미 SHA-256 전용이라 약하다. 공개 계약을 바꾸는 비용이 가장 작은 운영 배포 전에 해시로 바꿨다.

- 파일 입력은 `{type, sha256}`, 업로드 · 파일 목록 응답은 `sha256`, 다운로드는 `/api/files/{sha256}` 이다. 형식이 틀리거나 UUID 가 오면 400 이다.
- 사용자 · Job · Task 의 UUID 는 내용이 아니라 기록을 가리키므로 그대로 둔다.
- 같은 바이트의 생성 결과 행은 Task 이력을 위해 각각 남는다. 파일 식별자는 기록이 아니라 **내용**을 가리킨다.
- 기존 행은 변환하지 않는다. V8 은 해시 없는 행이 있으면 실패해, 파일을 잃은 채 기동하지 않는다.

GitLab 도 같은 갈림길에서 나눈다. LFS 는 클라이언트가 계산한 SHA-256 oid 를 식별자로 쓰고 프로젝트와의 링크로 접근을 확인한다([GitLab LFS](https://docs.gitlab.com/development/lfs/)).
URL 자체가 열쇠라 인증 없이도 열리는 이슈 첨부는 랜덤 32자 secret 을 쓴다([GitLab 첨부](https://docs.gitlab.com/security/user_file_uploads)). 우리 조회는 항상 인증된 소유자 범위라 LFS 쪽이다.

## 선택하지 않은 대안

| 대안 | 하지 않은 이유 |
|---|---|
| `Content-MD5` 로 내용 고정 (F5) | 고정은 되지만 키의 SHA-256 은 클라이언트의 말로 남는다. SHA-256 하나로 키와 강제를 겸한다(F7) |
| 1회용 주소 (`If-None-Match: *`) | Garage 가 지원하지 않는다(F4). 지원해도 재전송까지 막아 재시도가 깨진다 |
| 검증 후 최종 위치로 이동 · complete API | 내용이 서명에 묶이면 이동이 막던 바꿔치기가 일어나지 않는다. complete 는 클라이언트에게 호출 순서만 하나 더 지운다 |
| 업로드 뒤 앱이 전체를 읽어 해시 | 앱이 바이트를 받지 않으려고 presigned 를 골랐다. 검증 전 바꿔치기도 막지 못한다 |
| 결과물과 같은 `blobs/{hash}` 공유 | 업로드 쓰기 권한으로 결과물을 덮어쓸 수 있고, 한 객체를 두 행이 공유해 삭제에 참조 세기가 필요하다 |
| 사용자 사이 중복 제거 | 해시로 남의 파일 보관 여부를 떠볼 수 있다. GitLab LFS 는 프로젝트 사이에서 oid 로 중복을 제거하다가, 올린 내용을 검증하지 않아 oid · 크기만 알면 다른 프로젝트의 파일을 가져올 수 있었다([gitlab-workhorse#197](https://gitlab.com/gitlab-org/gitlab-workhorse/-/issues/197)) |
| 거절된 행을 다른 형식으로 다시 연다 (정정) | 위 "거절된 파일은 다시 열지 않는다" |
| 동시 최초 발급을 `INSERT … ON CONFLICT DO NOTHING` | 충돌하면 기존 행을 돌려주지 않아 어차피 다시 읽어야 한다. jOOQ 포트와 JPA 1차 캐시 정리가 따라붙는다 |
| 공개 식별자를 UUID 로 유지 | 소유자 안에서 해시와 1:1 이라 얻는 것이 없다. 알고리즘 고착은 키와 서명에 이미 있다 |
| 공개 식별자를 랜덤 secret 으로 | URL 자체가 열쇠일 때의 방식이다. 우리 조회는 항상 인증된 소유자 범위다 |
| 생성 결과를 내용 기준으로 한 행만 남긴다 | 어느 Task 가 만든 결과인지라는 이력을 잃는다 |
| 기존 행을 옮기는 변환 도구 | 운영 데이터가 없다. 로컬 DB 하나를 위해 일회성 도구와 그 테스트를 유지할 이유가 없다 |

## 검증 근거

- Garage `v2.4.1` 실험 F7 — 다른 내용 400 `InvalidDigest`, 해시를 고치면 403, 헤더를 빼면 400, 원본이 있는 자리에 다른 내용을 올려도 원본이 남는다
- `S3PresignedUploadIssuerTest` — 실제 Garage 에서 위를 고정하고, 같은 내용의 재전송은 허용됨을 확인한다
- `UploadedFileMigrationTest` — 기존 행이 있는 DB 에 V7 이 걸리고 옛 행이 그대로 남는다
- `UploadApiTest` · `UploadServiceTest` — READY 재사용은 보관소를 읽거나 쓰기 주소를 내지 않는다. 다른 사용자는 같은 해시라도 별도 행과 객체를 가진다.
  동시 최초 발급 4건이 한 행으로 모인다(2026-10-18 실행에서 3건이 유니크 제약을 거쳐 재조회했다).
  해시 자리에 UUID 나 잘못된 해시를 보내면 400 이다
- 샘플 페이지와 `upload.sh` 는 로컬 fixture 로 해시 · 헤더 · 중복 PUT 생략을 확인했다
- 같은 모양의 선례 — GitLab LFS 도 SHA-256 oid 와 크기로 객체를 하나만 두고, 접근은 프로젝트와의 링크로 확인한다([GitLab LFS](https://docs.gitlab.com/development/lfs/))

## 명시적으로 하지 않는 것

- 옛 행의 해시 소급. 객체를 읽어야 한다
- 기존 데이터 변환. 운영 배포 전이다
- 생성 결과 행의 중복 제거
- 사용자 사이 중복 제거
- 스트리밍 · 멀티파트 업로드
- 검증 후 이동과 complete API
- 디코드 · 재인코딩
- 거절된 내용의 정정 · 복구. 필요하면 운영자가 행을 지운다
- SDK. 같은 로직이 이미 두 클라이언트에 있다

## 다시 검토할 조건

- 보관소를 Garage 에서 바꾼다 → F7 을 다시 실험한다. 체크섬이 강제되지 않으면 내용 고정이 깨진다
- 크기 상한을 크게 올린다 → 클라이언트의 전체 해시 비용과 멀티파트 체크섬을 본다
- 외부 소비자가 생긴다 → 매직넘버 선언 · 해시 · 체크섬 헤더를 SDK 로 제공한다
- 거절로 막힌 사용자가 실제로 나온다 → 정정이나 행 삭제를 다시 본다. `UploadStatus.isFinal` 이 REJECTED 를 최종으로 두는 것부터 바꾼다
- 허용 형식이 늘어 클라이언트와 서버의 판별 규칙이 어긋날 수 있다 → 판별 규칙을 한 곳으로 모은다
- 해시 알고리즘을 바꿔야 한다 → 키 · 서명 · 공개 식별자를 함께 옮기는 변환이 필요하다. 해시를 공개 식별자로 쓴 대가다
- 해시가 소유자 범위 밖으로 나가는 경로(공개 공유 링크 등)가 생긴다 → 바이트를 가진 사람은 해시를 계산할 수 있으니, GitLab 첨부처럼 불투명한 별도 식별자를 둔다
- 같은 내용의 생성 결과 중 **특정 하나**를 가리켜야 하는 기능이 생긴다 → 기록 식별자(Task UUID 와 순번 등)를 따로 낸다

## 관찰할 metric과 log

- INFO `업로드 주소를 발급했다` · `검증된 같은 파일을 재사용한다` — 두 줄의 비율이 중복 적중률이다
- INFO `업로드를 검증했다. … status=… declared=… actual=…` — 공식 클라이언트에서 REJECTED 가 나오면 클라이언트와 서버의 판별 규칙이 어긋난 것이다
- WARN `거절된 파일을 다시 발급하려 했다. … rejected=… requested=…` — 막힌 사용자다. 다시 검토할 조건의 신호다
- WARN `중복 업로드 확인 중 보관소에 닿지 못했다` (503) · `불합격한 업로드를 지우지 못했다`
- SQL — 상태별 행 수, `generated_files` 에서 sha256 이 같은 행의 수(같은 내용의 생성 이력이 얼마나 생기는지)
- 해시 자리에 UUID 가 와서 난 400 — 옛 계약을 쓰는 클라이언트가 남아 있다는 신호다
- Hibernate WARN `SQLState: 23505` (`uploaded_files`) — 동시 최초 발급 경합의 빈도
