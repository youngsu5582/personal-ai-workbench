# ADR 0005. 요청의 주체는 사람과 사람이 만든 서비스이고, 소유와 관리는 사용자가 한다

- 상태: 제안
- 범위: `auth` · `user` · `generation` · `usage` 모듈
- 앞선 결정: [ADR 0003](0003-cost-separate-from-ledger.md) — 원장은 사실만 INSERT 한다

## 결정

- 요청의 **주체(principal)는 두 종류**다.
  - **사람** — 로그인한 사용자. 지금처럼 로그인으로 받은 토큰으로 부른다.
  - **서비스** — 사용자가 만들어 갖는, 이름 붙은 호출자(예: `youngsu-blog`). 서비스에 딸린 API Key 로 부른다.
- **소유 · 과금 · 관리의 최상위 단위는 사용자다.**
  - 서비스가 만든 작업 · 결과 · 사용 기록도 그 서비스를 가진 사용자의 것이다.
  - 사용자가 만드는 설정(서비스, 이후의 템플릿)도 사용자 소유이고, 그 사용자의 콘솔과 서비스가 함께 쓴다.
- **"누구 것인가"와 "누가 불렀나"를 따로 기록한다.** 소유는 사용자, 호출자는 콘솔 또는 서비스다.
- **서비스는 관리되는 쪽이다.** 서비스를 만들고 · 키를 발급 · 교체하고 · 끄고 · 권한을 정하는 일은 그 서비스를 가진 사용자만 한다.
  서비스는 자기 키나 다른 서비스를 만들 수 없다.
- 사람과 서비스는 **같은 API** 를 부른다. 무엇을 할 수 있는지는 주소가 아니라 들고 온 자격 증명이 정한다.
- 서비스는 **자기가 부른 작업만** 본다. 사람은 자기 소유의 작업을 서비스가 만든 것까지 모두 본다.

## 문제와 사용자 영향

- 지금 주체는 로그인한 사람뿐이다. 블로그 같은 서버가 워크벤치를 부르려면 사람의 토큰을 서버에 넣어야 하는데,
  그러면 사람이 할 수 있는 모든 일이 그 서버에 열리고, 토큰의 만료와 갱신을 사람이 챙겨야 한다.
- 누가 불렀는지가 남지 않는다. 같은 사용자의 작업이 콘솔에서 온 것인지 어느 서비스에서 온 것인지 가를 수 없어,
  서비스별 비용도, 이상하게 많이 쓰는 호출자도 알 수 없다.
- 사용자가 여럿이 되면 서비스가 **누구의 것인지**가 정해져 있어야 한다. 주인이 없는 서비스는 키를 바꾸거나 끌 사람이 없다.

## 제약 조건

- 사용자는 언제든 여럿이 될 수 있어야 한다. 한 사람을 전제로 한 구조를 두지 않는다.
- 워크벤치는 호출하는 서비스의 목적을 해석하지 않는다. 서비스는 이름과 권한을 가진 호출자일 뿐이다.
- 서비스의 자격 증명은 그 서비스의 서버에만 있다. 브라우저로 내려가는 경로를 만들지 않는다.
- 작업 · 업로드 · 원장의 소유 칸은 이미 사용자(`owner_user_uuid`) 하나다.
- 원장(`provider_calls`)은 집계 축을 조인 없이 답한다 — 소유 사용자를 복사해 두는 것과 같은 이유로 호출자도 복사한다.

## 선택한 해법

```text
사용자 (소유 · 과금 · 관리의 최상위)
 ├─ 서비스 youngsu-blog            ← 이름 · 권한 · 켜짐/꺼짐
 │    ├─ API Key (지금 것)          ← 교체할 때만 둘
 │    └─ API Key (다음 것)
 ├─ 템플릿 …                        ← 사용자 소유, 그 사용자의 서비스가 함께 씀
 └─ 작업 · 사용 기록                 ← 소유 = 사용자, 호출자 = 콘솔 | 서비스

사람 ── 로그인 토큰 ──┐
                      ├──▶ 같은 API ──▶ 주체 = (소유 사용자, 호출자, 권한)
서비스 ── API Key ────┘
```

### 주체를 정하는 곳

- 요청마다 자격 증명을 **주체 하나**로 바꾼다. 주체는 소유 사용자 · 호출자 · 권한을 함께 든다.
- 사람 토큰이면 소유 사용자 = 그 사람, 호출자 = 콘솔, 권한 = 전부.
- API Key 면 소유 사용자 = 그 서비스의 주인, 호출자 = 그 서비스, 권한 = 서비스에 준 것.
- 요청 본문이나 헤더가 말하는 서비스 이름 · 소유자는 믿지 않는다. 자격 증명에서만 정한다.

### 자격 증명 — API Key

- 키는 서비스에 딸린다. 서비스 하나에 **동시에 살아 있는 키는 두 개까지**다. 새 키를 만들고 호출자 쪽을 바꾼 뒤 옛 키를 끄는 것으로 끊김 없이 교체한다.
- 키는 만들 때 한 번만 보여 주고, 원문 대신 **SHA-256 해시만 저장**한다. 요청이 오면 받은 키를 같은 방식으로 해시해 인덱스로 찾는다.
  - 비밀번호처럼 느린 해시(bcrypt · argon2)를 쓰지 않는다. 키는 무작위 256비트라 대입으로 맞힐 수 없어 느리게 만들 이유가 없고,
    행마다 다른 소금이 붙으면 해시로 바로 찾을 수 없어 요청마다 모든 키를 대조해야 한다.
- 키는 사람 토큰과 **같은 `Authorization: Bearer` 헤더**로 받는다. 키에는 앞머리(`wb_sk_`)를 붙이고,
  서버는 앞머리로 확인 방식을 고른다 — `wb_sk_` 면 해시 조회, 그 밖이면 JWT 서명 확인.
  요청 하나에 자격 증명은 하나뿐이고, 새어 나간 키를 알아보기도 쉽다.
- 키를 끄면 **그 즉시** 막힌다. 서비스를 끄면 그 서비스의 모든 키가 막힌다.

### 권한

- 권한(scope)은 키가 아니라 **서비스에** 붙는다. 키를 바꿔도 권한은 그대로다.
- 단위는 결과물 종류와 행위다(글 생성 · 이미지 생성 · 작업 조회 …). 서비스의 쓰임새 이름으로 짓지 않는다.
- 사람 토큰은 모든 권한을 갖는다. 엔드포인트는 주체의 종류를 묻지 않고 권한만 본다.
- 서비스 관리 API(서비스 · 키 만들기와 끄기)는 사람만 부른다.

### 기록

- 작업과 원장에 **호출자**(콘솔 | 서비스)를 둔다. 서비스별 사용량과 비용은 이 칸으로 가른다.
- 어느 키였는지는 로그에 키의 앞부분만 남긴다. 키 원문은 어디에도 남기지 않는다.
- 서비스를 나누는 기준은 하나다. **권한 · 소유 · 비용 중 하나라도 달라야 하면 서비스(와 키)를 나누고**,
  같은 서비스 안의 쓰임새를 기록으로만 나누려면 요청의 이름표(`operation`)를 쓴다. 이름표는 해석하지 않고 권한 판단에 쓰지 않는다.

### 저장 모양 (윤곽)

칼럼 정의는 구현의 마이그레이션이 정한다. 여기에는 테이블이 무엇을 뜻하는지와 지킬 것만 둔다.

| 테이블 · 칸 | 한 행의 뜻 | 지키는 것 |
|---|---|---|
| `services` | 사용자가 만든 호출자 하나 — 소유 사용자 · 이름 · 권한 · 켜짐/꺼짐 | 한 사용자 안에서 이름이 겹치지 않는다 |
| `service_api_keys` | 그 서비스로 들어오는 출입증 하나 — 해시 · 앞부분 · 켜짐/꺼짐 | 서비스당 켜진 키는 두 개까지. 원문은 저장하지 않는다 |
| `generation_jobs` · `provider_calls` 의 호출자 칸 | 그 작업 · 호출을 누가 불렀나 — 콘솔 또는 서비스 하나 | 소유 칸과 따로 둔다. 원장 쪽은 소유 칸처럼 FK 를 두지 않는다 — 돈을 쓴 뒤의 INSERT 가 제약에 걸리면 안 된다 |

## 선택하지 않은 대안

- **서비스를 독립 계정(사용자 행)으로 둔다** — 서비스별 집계는 기존 소유 칸으로 되지만, 서비스의 주인이 비어 관리 주체가 없다.
  사용자가 여럿이면 누가 그 키를 바꾸고 끄는지 정할 수 없다.
- **서비스가 사람을 대리한다**(사람 토큰이나 개인 액세스 토큰을 서버에 넣는다) — 사람의 권한 전체가 서버에 열리고, 호출자를 가를 수 없다.
- **client_credentials 로 짧은 토큰을 발급한다** — 이미 나간 토큰은 만료 전까지 막을 수 없고, 토큰 보관 · 갱신이 호출하는 쪽에 생긴다.
  지금 규모에서는 키를 끄면 즉시 막히는 쪽이 더 쓸모 있다.
- **서비스에도 오래 사는 JWT 를 발급한다** — 서버가 장부를 보지 않고 서명만 확인하므로, 끄려면 결국 "끈 토큰 목록"을 요청마다 봐야 한다.
  권한이 발급 때 토큰 안에 박혀, 서비스의 권한을 바꿔도 이미 나간 토큰에는 반영되지 않는다.
  사람 토큰은 수명이 짧아 이 두 문제가 없으므로 JWT 를 그대로 둔다.
- **API Key 를 전용 헤더(`X-API-Key`)로 받는다** — 사람 토큰과 키가 함께 오면 무엇을 믿을지 규칙이 하나 더 필요하다.
  임의 헤더는 프록시 · 로그 도구가 `Authorization` 처럼 가려 주지 않는 경우가 많다.
- **키 단위로 권한을 주고 기록한다** — 키를 바꾸면 기록이 끊겨 보이고 권한을 키마다 다시 정해야 한다.
- **그룹(프로젝트)을 먼저 둔다** — 묶을 사람이 아직 없는데 모든 소유 확인이 "사용자이거나 소속 그룹"으로 바뀐다.
- **서비스용 API 를 따로 만든다** — 같은 동작이 두 벌이 되어 검증 · 테스트 · 문서가 갈라진다.

## 검증 근거

- 작업 · 업로드 · 원장의 소유 칸이 이미 사용자 하나라, 이 결정이 더하는 칸은 호출자뿐이다. 소유 확인 코드는 바뀌지 않는다.
- 선례
  - Google Cloud 서비스 계정 — 애플리케이션을 위한 주체이면서, 다른 주체가 관리하는 리소스다.
    서비스를 "요청하는 주체이자 사용자가 관리하는 대상"으로 두는 이 결정과 같은 구조다.
  - OpenAI · Stripe — 계정이 이름 붙은 API Key 를 만들고 끄며, 키는 만들 때 한 번만 보여 준다. 사용량을 키 · 프로젝트별로 본다.
  - GitHub — 사람 토큰과 앱 토큰이 같은 API 를 부르고, 무엇을 할 수 있는지는 토큰의 권한이 정한다. 소유자는 개인 또는 조직이다.
    토큰 종류를 앞머리로 드러내고 구분자로 `_` 를 쓴다 — base64 에 없는 글자라 다른 문자열과 겹치지 않는다.
- 성립해야 할 식
  - 모든 작업은 소유 사용자를 정확히 하나 갖는다.
  - 서비스의 키로 만든 작업의 소유 사용자 = 그 서비스의 소유 사용자.
  - 서비스의 키로 조회할 수 있는 작업 ⊆ 그 서비스가 부른 작업.
  - 서비스에 동시에 살아 있는 키 ≤ 2.

## 명시적으로 하지 않는 것

- 그룹 · 조직과 역할(관리자 · 멤버)
- 서비스별 예산 · 모델 제한
- 서비스의 쓰임새(`operation`) 허용 목록 — 받더라도 추적용 이름표로만 둔다
- 권한 목록의 세부 — 붙는 자리(서비스)와 단위(결과물 · 행위)만 정한다
- 서비스 · 키를 관리하는 콘솔 화면
- 템플릿 자체 — 소유 규칙(사용자 소유)만 이 결정을 따른다

## 다시 검토할 조건

- 여러 사용자를 하나로 묶을 팀이 필요해질 때 → 소유자를 "사용자 또는 그룹"으로 넓힌다. "누구 것인가"와 "누가 불렀나"를 나눠 둔 것은 그대로 쓴다.
- 한 서비스가 여러 키를 동시에 상시 쓸 때 → 원장에 키 칸을 더한다.
- 서비스와 호출이 늘어 요청마다 키를 확인하는 비용이 보일 때 → 확인 결과 캐시, 또는 짧은 토큰으로 바꿔 주는 방식을 다시 본다.

## 관찰할 metric과 log

- 서비스별 호출 수와 비용 — 원장의 호출자 축
- 인증 실패 수 — 서비스 이름과 키 앞부분만 태그로 남긴다
- 꺼진 키 · 꺼진 서비스로 들어온 요청 수
