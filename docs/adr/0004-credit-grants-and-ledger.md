# ADR 0004. 호출자별 크레딧은 지급 묶음과 원장으로 둔다

- 상태: 제안 (2026-10-18). 구현 PR 이 머지되면 채택으로 바꾼다
- 범위: 새 `credit` 모듈, `generation` 의 접수(`GenerationJobWriter.create`)와 최종 실패(`TaskStateWriter.fail`)
- 앞선 결정: [ADR 0003](0003-cost-separate-from-ledger.md) — 비용은 우리가 낸 돈이고 크레딧과 다르다

## 결정

호출자(`owner_user_uuid`)가 무엇을 얼마나 쓸 수 있는지를 **크레딧**으로 정한다.

- 크레딧은 비용에서 파생하지 않는다. 우리가 정한 **요청 단위 가격**(모델 + 품질 → 장당 N 크레딧)이다.
- 크레딧은 **묶음(grant)** 으로 들어온다. 출처는 DAILY · MONTHLY · ADMIN · PURCHASE 이고, 묶음마다 양 · 남은 양 · 만료가 있다.
  기간 한도는 따로 두지 않는다 — "만료가 있는 월간 묶음" 이 기간 한도다.
- 일간 · 월간 묶음은 **지급 정책**(묶음과 다른 테이블)을 보고, 그 호출자를 그 기간에 처음 볼 때 **게으르게** 만든다.
- 접수할 때 Task 마다 단가만큼 **소비 순서**(만료 임박 → 무료 → 유료 → 오래된 순)대로 묶음에서 꺼낸다.
  Job 기록과 같은 트랜잭션이고, 모자라면 Job 까지 롤백하고 402 로 거절한다.
- 최종 실패한 Task 는 꺼낸 묶음으로 되돌린다. **만료된 묶음 몫은 돌려주지 않고 FORFEITED 로 기록한다.**

테이블은 다섯이다.

| | 테이블 | 한 행의 뜻 |
|---|---|---|
| 정책 | `credit_prices` | 이 모델 · 품질은 장당 N 크레딧 (기간) |
| 정책 | `credit_grant_policies` | 누구에게(NULL = 모두) 어떤 주기로 얼마를 준다 (기간) |
| 사실 | `credit_grants` | 들어온 묶음. `remaining` 만 바뀐다 |
| 사실 | `credit_ledger_entries` | 움직인 사실 — Task 별 CHARGE · REFUND. append-only |
| 사실 | `credit_allocations` | 그 움직임이 어느 묶음에서 얼마였나 — CHARGED · RETURNED · FORFEITED |

**묶음은 들어온 기록, 원장은 움직인 기록, 할당은 둘을 잇는 기록이다.** 잔액은 저장하지 않는다 — 살아 있는 묶음의 `remaining` 합이다.

## 문제와 사용자 영향

- 이 워크벤치의 호출자는 내 서비스들이다. 한 서비스의 버그 · 반복 호출이 Provider 예산 전체를 태울 수 있는데, 지금은 막는 것이 없다.
  비용(ADR 0002 · 0003)은 호출이 끝난 **뒤에** 알게 되므로 막는 데 쓸 수 없다.
- 호출자마다 쓸 수 있는 모델 · 품질을 정해 둘 방법이 없다. 같은 모델도 품질에 따라 장당 비용이 약 35배 갈린다(gpt-image-2 1024², low $0.006 · high $0.211).
- 크레딧이 들어오는 길은 하나가 아니다 — 매일 · 매달 주는 것, 운영자가 따로 주는 것, 나중에는 충전. 길마다 시스템을 따로 두면 "어느 것부터 쓰나" 를 정할 자리가 없다.

## 제약 조건

- 접수는 트랜잭션 밖에서 입력을 확인하고(보관소를 탄다), `GenerationJobWriter.create` 의 트랜잭션에서 Job · Task 를 기록한다. 차감은 그 트랜잭션 안이어야 한다.
- Task 하나가 Provider 호출 한 번이고 결과물 한 장이다. 재시도로 같은 Task 가 최대 3번 호출된다.
- 품질의 기본값이 `AUTO` 다 — Provider 가 품질을 고르므로 접수 시점에는 실제 품질을 모른다.
- 관리자 개념이 없다. 접근 통제는 `AUTH_ALLOWED_EMAILS` 뿐이다.
- RUNNING 고착을 회수하는 기능이 없다. 워커가 죽으면 Task 가 RUNNING 에 남는다.
- 같은 DB 를 쓰는 모듈러 모놀리스다. 모듈 경계를 넘을 때는 포트와 값만 넘긴다 (CLAUDE.md).

## 선택한 해법

**지급.** 정책은 출처마다 호출자 행이 있으면 그것, 없으면 기본(owner NULL)을 쓴다. 이번 기간 묶음이 없으면
`INSERT … ON CONFLICT (owner_user_uuid, source, ref) DO NOTHING` 으로 만든다 — `ref` 는 DAILY `YYYY-MM-DD`, MONTHLY `YYYY-MM`.
스케줄러가 없고, 몇 번 불러도 한 번만 지급된다. 일 · 월 경계는 UTC 로 `/api/usage` 의 "이번 달" 과 같다.
ADMIN · PURCHASE 는 운영 SQL · 결제 흐름이 직접 넣고, `ref` 가 같은 지급의 중복을 막는다.

**차감.** 그 호출자의 살아 있는 묶음을 소비 순서대로 `FOR UPDATE` 로 잠그고 꺼낸다.
모든 트랜잭션이 같은 순서로 잠가 교착이 없다. Task 마다 원장 CHARGE 한 줄과 할당 CHARGED 1~2줄을 쓴다.
단가는 트랜잭션 안에서 다시 정한다 — 밖에서 읽은 값을 넘기면 그 사이 단가표의 경계가 지나갈 수 있다.

**환불.** 환불은 **"그 요청이 없었던 상태로 되돌리기"** 다. 요청이 없었어도 만료된 묶음의 크레딧은 이미 사라졌을 것이므로 돌려주지 않는다.

```text
10-18 23:59  high 1장(22) 접수 → DAILY(10-18, 남은 10) 에서 10, MONTHLY(10월) 에서 12
10-19 00:03  최종 실패 → 환불
             MONTHLY 12  → RETURNED   (살아 있다, remaining 을 되돌린다)
             DAILY   10  → FORFEITED  (00:00 에 만료됐다, 묶음은 건드리지 않는다)
             원장 REFUND +12
```

돌려주지 않은 몫도 FORFEITED 로 남긴다. 남기지 않으면 셋을 판단할 수 없다 —
그 Task 의 환불을 처리했는지(전부 만료된 몫이면 아무 행도 안 생긴다), 빠진 양이 정책인지 버그인지, 그런 일이 얼마나 자주인지.
그래서 REFUND 행은 0 이어도 쓰고, `UNIQUE (kind, task_uuid)` 가 두 번 처리를 막는다.

**경계.** generation 은 `credit` 루트 포트에 값만 넘긴다 — 접수 전 `quote(model, quality)`, 기록 트랜잭션 안의 `charge(…)`,
최종 실패 트랜잭션 안의 `refund(taskUuid)`. 포트가 generation 의 트랜잭션에 **참여한다**는 것이 계약의 일부다.

**응답.** 크레딧 부족은 402 + `required` · `available` · `nextGrantAt`, 단가 없는 요청은 400 이다.

## 선택하지 않은 대안

| 대안 | 하지 않은 이유 |
|---|---|
| 비용(USD)에서 크레딧을 계산한다 | 비용은 호출 뒤에야 안다. 접수할 때 막을 수 없고 호출자가 미리 값을 알 수 없다 |
| 기간 한도만 (`credit_usage(owner, period, used)` 카운터) | 지급 길이 하나뿐이다. 운영 지급 · 충전이 들어오는 순간 "무엇부터 쓰나" 를 둘 자리가 없다 |
| 충전형 잔액만 (`balance` 한 칸) | 매일 · 매달 주는 것과 만료를 표현할 수 없다. 남은 양이 어느 지급에서 왔는지 모른다 |
| 일간 · 월간 지급을 스케줄러로 | 놓친 주기를 다시 채우는 일이 생긴다. 게으른 지급은 재시작 · 장애에도 두 번도, 빠뜨리지도 않는다 |
| 지급 정책을 설정 파일에 | 호출자별 예외는 DB 에 있어 규칙이 두 곳으로 나뉜다 |
| 묶음마다 `priority` 숫자 | 지급할 때마다 사람이 숫자를 맞게 정해야 하고, 틀려도 막는 것이 없다 |
| 원장에 GRANT 도 적는다 | 묶음 행이 이미 들어온 기록이다. 같은 사실이 두 곳에 생긴다 |
| 할당을 원장 행의 jsonb 로 | 모양이 고정이고 묶음 기준으로 묻는 쿼리(검산 · 이력 · FORFEITED 합)가 생긴다. FK · CHECK 를 걸 수 없다 — 이 저장소가 jsonb 를 고르는 이유(모양이 갈리고 안을 집계하지 않는다)와 반대다 |
| 한 문장 조건부 UPDATE 로 차감 | 여러 묶음에서 나눠 꺼내야 해서 한 문장으로 되지 않는다 |
| 만료된 몫은 새 REFUND 묶음으로 돌려준다 | 요청이 없었다면 사라졌을 크레딧을 새로 준다. 자정 직전에 실패할 요청을 보내 곧 사라질 크레딧을 연장하는 길이 열린다 |
| 크레딧 부족을 429 로 | 클라이언트가 "잠깐 뒤 재시도" 로 읽으면 버그 난 호출자가 부족 응답에 재시도를 퍼붓는다 — 막으려던 바로 그 일이다 |
| 호출자별 단가 · 허용 목록부터 | 갈라야 할 실제 사례가 없다. 나중에 `credit_prices` 에 owner 칸을 nullable 로 더하면 기존 행이 그대로 전역이 된다 |

## 검증 근거

- `GenerationJobService` 는 차감이 들어갈 자리를 접수의 판단 쪽으로, 차감과 기록을 같은 트랜잭션으로 정해 두었다.
  `TaskStateWriter.fail` 의 재시도하지 않는 분기가 Task 가 최종 실패하는 유일한 자리다.
- [Image generation guide](https://developers.openai.com/api/docs/guides/image-generation) 의 장당 비용 표 — 같은 모델에서 품질이 비용을 가장 크게 가른다.
  단가 키에 품질이 들어가는 근거다.
- 검산의 기준 — 묶음마다 `remaining = amount − ΣCHARGED + ΣRETURNED`, 환불된 Task 마다 `ΣCHARGED = ΣRETURNED + ΣFORFEITED`.
  `remaining` 을 캐시로 두어도 되는 이유가 이 두 식이다.

## 명시적으로 하지 않는 것

- 결제 · 충전 흐름 — PURCHASE 출처와 `ref` 자리만 둔다
- 사용 상한(cap) — "하루 최대 N 사용" 같은 가드는 잔액과 별개로 나중에 더한다
- 운영 차감(ADJUST) — 크레딧을 늘리는 일은 ADMIN 묶음 지급으로 한다
- 호출자별 단가, 크기별 단가, 견적 API
- 그룹(조직)별 크레딧 — billing account 가 생긴 뒤
- 크레딧 소비와 실제 비용(USD)의 대사 화면 — 운영 콘솔

## 다시 검토할 조건

- 충전 크레딧이 들어와 큰 잔액이 쌓인다 → 사용 상한. 지급량이 더는 상한 역할을 하지 못한다
- 유료(PURCHASE) 크레딧에 만료를 둔다 → FORFEITED 규칙. 그때부터 잃는 것이 무료 크레딧이 아니라 돈이다
- 호출자 한 명의 요청이 몰려 묶음 잠금이 병목이 된다 → 호출자 단위 직렬화를 다시 본다
- 서버를 나눈다 → 차감과 Job 기록이 한 트랜잭션일 수 없다. 예약 → 확정(사가)으로 바꾼다
- 만료로 못 돌려준 양(FORFEITED 합)이 눈에 띄게 쌓인다 → 일간 경계를 한국 자정으로 옮기거나 환불 유예를 둔다
- 호출자마다 쓸 모델 · 품질을 달리해야 할 사례가 생긴다 → 호출자별 단가

## 관찰할 metric과 log

- metric — `workbench.credit.charge`(차감한 크레딧) · `workbench.credit.refund`(돌려준 크레딧, `outcome` = returned · forfeited) ·
  `workbench.credit.rejection`(부족으로 거절한 접수) 카운터. 태그는 `model` 까지다 — 호출자를 태그로 두면 호출자 수만큼 시계열이 늘어, 호출자별로는 로그와 SQL 로 본다
- INFO log — 차감(호출자 · Task 수 · 크레딧 · 꺼낸 묶음 수), 환불(RETURNED · FORFEITED 양)
- WARN log — 크레딧 부족으로 거절(호출자 · 필요 · 가용). 같은 호출자가 짧은 사이에 반복하면 그 서비스가 응답을 무시하고 있는 것이다
- SQL — 출처별 지급량 대비 소비량, FORFEITED 합, 만료 때 남은 양(만료된 묶음의 `remaining` 합)
- SQL — 검산 셋(묶음별 `remaining`, 원장과 할당의 합, Task 별 CHARGED = RETURNED + FORFEITED). 어긋나는 행이 0 이어야 한다
