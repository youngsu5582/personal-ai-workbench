# 작업 내역 가독성 SPEC

## 1. 확인한 사실

- 블로그는 프롬프트를 직접 보내지 않고 템플릿을 실행한다(`/api/templates/{uuid}/jobs` 에 `variables` 만). 템플릿 처음 정의는 블로그의 `lib/workbench-templates.ts`, 정본은 콘솔. 메타데이터 템플릿에 `{{title}}` 변수가 있다.
- `GenerationTemplateService.submit` 은 채운 옵션만 Job 에 넘긴다. Job 에는 어느 템플릿에서 왔는지 · 어떤 변수였는지 · 어느 키로 불렀는지가 남지 않는다.
- 메타데이터 · 번역 프롬프트에는 글 본문 전체가 들어 있다. 원문 검색은 본문에서 언급만 한 다른 글의 작업까지 건다.
- 처리 시간(`startedAt`~`finishedAt`)은 Provider 호출과 결과 보관을 합친 것이다. 둘로 나눈 값은 이미지 작업의 완료 로그(`provider=` · `보관=`)와 `workbench.storage.write` 지표에 있다.

## 2. 결정

- **D1 처리 시간은 나누어 보이지 않는다.** 사용자가 그 차이로 할 수 있는 일이 없다. 운영자용은 로그 · 지표에 있다. 막대에 "처리 = 모델 호출 + 결과 보관" 툴팁만 둔다.
- **D2 목록 상태는 배지 하나.** `CLOSED` 를 그대로 보이지 않고 `progress` 로 성공 · 일부 실패 · 실패를 가른다. 결과가 2개 이상일 때만 개수를 붙인다.
- **D3 날짜는 묶음 머리로 올리고 행에는 시각만.**
- **D4 작업 이름은 템플릿에 정한 이름 틀을 실행 변수로 채운다.** 요청마다 `label` 을 보내는 안은 버렸다 — 소비자 코드를 고쳐야 하고 같은 템플릿의 이름 모양이 흩어진다. 틀이 없으면 템플릿 이름, 템플릿이 아니면 프롬프트를 보인다. 채운 이름은 접수 때 Job 에 저장한다(템플릿이 바뀌어도 옛 이름 유지).
- **D5 출처는 템플릿 / 직접 요청까지만.** 호출 키(콘솔 · 서비스 키) 출처는 보류 — 지금은 블로그 요청과 템플릿 요청이 같은 집합이다.
- **D6 검색은 이름(+ 템플릿 이름)에서만.** 이름 없는 작업(직접 요청 · 이 기능 전 작업)은 못 찾고, 맞춰 주는 추출 코드를 넣지 않는다. 원문 검색이 필요해지면 pg_trgm 부터, OpenSearch · 벡터는 답할 질문이 생긴 뒤.

## 3. PR 2 설계 초안 (미확정)

- Job: 템플릿 참조(uuid) + 이름 컬럼. 템플릿 삭제 시 처리 방식은 설계 때 정한다
- 템플릿: 선택 필드 이름 틀. 변수 문법은 기존 `{{name}}` 과 같고, 없는 변수는 접수 400
- 목록 API: `GET /api/jobs?q=&template=` — `q` 는 서비스 범위 안에서 이름 · 템플릿 이름 `ILIKE`
- 콘솔: 목록 위 검색창(안내 "이름으로 찾기") + 템플릿 필터, 검색 중 이름이 없어 빠진 건수 안내
