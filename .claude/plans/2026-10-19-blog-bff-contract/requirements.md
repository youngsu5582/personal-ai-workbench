# 블로그 BFF 연결을 위한 Workbench 요구사항

출발점: 블로그 명세 `Homeserver/Homelab/Projects/Personal AI File Inbox/09 Blog BFF Implementation Specification.md` 의 7절(Workbench 선행 계약).
목표: 블로그 BFF 가 Provider 를 직접 부르지 않고 Workbench 로 글 생성을 맡기고, 결과 · 사용량 · 실패를 requestId 하나로 따라간다.

상태 표기: ✅ 있음 · 🔺 일부 · ❌ 없음 (2026-10-19 main 기준)

## 주체와 소유 — ADR 0005

- 사용자가 소유 · 과금 · 관리의 최상위 단위다. 사용자는 언제든 여럿이 될 수 있어야 한다.
- 서비스는 사용자가 만들어 갖는 이름 붙은 호출자다. 서비스에 API Key 가 딸린다(교체용으로 두 개까지).
- 기록은 "누구 것인가"(사용자)와 "누가 불렀나"(콘솔 | 서비스)를 나눈다.
- 템플릿도 사용자 소유다(만드는 것은 나중).
- 그룹은 나중. 필요해지면 소유자를 "사용자 또는 그룹"으로 넓힌다.

## 기능 요구사항

### R1. 글 생성 실행
| ID | 요구사항 | 수용 기준 | 지금 |
|---|---|---|---|
| R1.1 | 프롬프트 · instructions · 형식(text / JSON Schema) · effort · 모델로 글을 만든다 | — | ✅ #66 |
| R1.2 | 동기처럼 받을 수 있다 | `Prefer: wait=N` → N초 안에 끝나면 200 + 결과, 아니면 202 + Job uuid. 서버 상한을 넘는 N 은 깎고 `Preference-Applied` 로 알림 | ❌ (결정 ②) |

응답 필드는 이미 충분하다 — `uuid`(answerId) · `status` · `model` · `tasks[].texts[].content`. Provider 이름은 내보내지 않는다(호출자는 모델만 안다). requestId 는 R5.

### R2. 서비스와 API Key (ADR 0005)
| ID | 요구사항 | 수용 기준 | 지금 |
|---|---|---|---|
| R2.1 | 사용자가 서비스를 만들고 끈다 | 서비스 = 이름 · 권한 · 켜짐/꺼짐 · 소유 사용자. 관리 수단은 결정 ⑦ | ❌ |
| R2.2 | 서비스에 API Key 를 발급하고 끈다 | 만들 때 한 번만 보여 줌 · 해시만 저장 · 앞머리 `wb_sk_` · 살아 있는 키 ≤ 2 · 끄면 즉시 막힘 | ❌ |
| R2.3 | 자격 증명을 주체로 바꾼다 | 사람 토큰 → (그 사람, 콘솔, 전부) / API Key → (서비스 주인, 서비스, 서비스 권한). 본문 · 헤더의 서비스 이름 · owner 는 믿지 않음 | 🔺 사람 토큰 → 사용자만 |
| R2.4 | 권한(scope)으로 막는다 | 권한 밖이면 403. 목록은 TODO — 단위는 결과물 종류 · 행위 | ❌ |
| R2.5 | 서비스는 자기가 부른 작업만 본다 | 다른 작업은 404 | ❌ |
| R2.6 | 키를 남기지 않는다 | 로그 · 응답에 원문 없음. 로그에는 앞부분만 | — |

### R3. 멱등
| ID | 요구사항 | 수용 기준 | 지금 |
|---|---|---|---|
| R3.1 | 같은 요청을 다시 보내면 기존 Job 을 돌려준다 | 같은 소유자 · 같은 `Idempotency-Key` · 같은 요청이면 Provider 를 다시 부르지 않음 | ❌ |
| R3.2 | 같은 키, 다른 내용이면 거절한다 | 409 + 안정 code | ❌ |
| R3.3 | 동시에 같은 키가 와도 Job 이 하나만 생긴다 | DB 유니크 제약 | ❌ |

### R4. 오류 정규화
| ID | 요구사항 | 수용 기준 | 지금 |
|---|---|---|---|
| R4.1 | 실패를 안정적인 code 로 낸다 | Provider 원문은 응답에서 빼고 DB · 로그에만 | 🔺 응답이 `[openai 400 …]` 원문을 냄 |
| R4.2 | Task 가 실패 종류를 기억한다 | 조회 응답의 code 가 여기서 나옴 | ❌ (원장에만 있음) |
| R4.3 | Provider 인증 실패를 따로 가른다 | Provider 401 · 403 → 우리 키 문제, 재시도하지 않음 | ❌ (`REJECTED` 에 섞임) |
| R4.4 | 접수 단계 오류도 같은 모양 | `{code, message, requestId}` | 🔺 ProblemDetail 은 있으나 code 가 없음 |

code 초안: `PROVIDER_TIMEOUT` · `PROVIDER_RATE_LIMITED` · `PROVIDER_UNAVAILABLE` · `PROVIDER_REJECTED` · `PROVIDER_AUTH_FAILED` · `OUTPUT_INCOMPLETE` · `UNKNOWN`,
요청 단계 `INVALID_REQUEST` · `UNSUPPORTED_MODEL` · `IDEMPOTENCY_CONFLICT` · `UNAUTHENTICATED` · `FORBIDDEN`. 블로그 명세 5.3 의 오류 표와 맞춰 확정한다.

### R5. 요청 추적
| ID | 요구사항 | 수용 기준 | 지금 |
|---|---|---|---|
| R5.1 | `X-Request-Id` 를 받고, 없으면 만든다 | 응답 헤더로 되돌림 | ❌ |
| R5.2 | 로그에 requestId | 접수 요청과 비동기 워커 양쪽. 워커는 Job 에서 복원 | ❌ |
| R5.3 | Job 이 requestId 를 기억하고 조회 응답에 담는다 | requestId → Job → 원장(job_uuid) → 비용 | 🔺 Job → 원장 → 비용은 있음 |
| R5.4 | `operation` 을 추적용 이름표로 받는다 | 해석하지 않고 Job 에 저장 | ❌ |

### R6. 기록
| ID | 요구사항 | 지금 |
|---|---|---|
| R6.1 | provider · model · 토큰 · 지연 · 성공/실패 · 실패 종류 · 비용(모르면 null) | ✅ |
| R6.2 | 호출자(콘솔 · 서비스)를 작업과 원장에 남긴다 | ❌ (R2 와 함께) |
| R6.3 | 사용량 조회를 서비스별로 나눠 본다 | ❌ |

## 비기능 요구사항

- 프롬프트 · 본문 · 키 · 토큰을 로그에 남기지 않는다. Provider 원문 응답을 바깥으로 내보내지 않는다.
- 블로그와 같은 요청/응답 예시(fixture)로 양쪽 계약을 고정한다.
- `Prefer: wait` 는 요청 스레드를 붙잡는다 — 대기 상한과 동시 대기 수 상한을 둔다.
